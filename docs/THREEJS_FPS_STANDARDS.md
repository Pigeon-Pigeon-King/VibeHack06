# Three.js FPS 技术规范

适用项目：《重返木卫三》。整理日期：2026-10-30，状态更新：2026-10-31。本文是开发与验收依据；当前已有三条缩短机制白盒及 S01→S07 连续开发流程，实现覆盖及尚未满足的规范见 [当前验证记录](../artifacts/transfer-evidence.md)。

规范分三层：**API／格式事实**来自官方文档；**项目要求**来自当前用户与交接分册；**工程建议**是待实机验证的实现路线。字段名、数值预算和状态枚举若标为建议，不应被误称为 Three.js 官方标准。

## 1 工程与依赖

项目要求：Three.js 展现、桌面键鼠优先、Mac 开发、最终 Windows EXE。建议 TypeScript＋Vite 管理运行工程，Electron 为桌面封装候选。构建与运行依赖留在项目内部，不依赖源机盘符或兄弟目录。

工程要求：固定 Three.js 与 addons 的兼容版本，提交锁文件；示例代码先逐模块理解再迁移。避免同时加载两份 Three.js，或从不同 CDN 版本混用核心库与加载器。首个技术验证同时验证浏览器入口和桌面容器的资源加载。

参考：[Three.js 源码与许可证](https://github.com/mrdoob/three.js)、[Electron](https://www.electronjs.org/docs/latest/)。旧示例版本清单见 [参考资料](REFERENCE_PROJECTS.md)。

## 2 单位、坐标与地图

API／格式事实：glTF 使用右手坐标、米制、+Y 向上、资产正面 +Z；Three.js 相机默认朝自身 −Z。Blender 编辑空间通常 Z 向上，导出器可以执行坐标转换。

项目约定建议：

- 世界单位为米、时间为秒、内部角度为弧度；界面显示角度时明确转换。
- +Y 向上、−Z 为地理北、+X 为东。模型本地朝向、枪口轴向和地图地理方向分别声明。
- 旧地图 Z 高程先按原元数据转换；Blender 导出完成的 Y-up 模型不再手工重复旋转。
- 角色眼高、碰撞胶囊与模型尺寸统一；儿童、成人、受伤和协作状态分别配置。
- 门宽、担架转角和车辆通路用实际代理尺寸验证，地图图示不能替代可通行检查。

验收：米制标尺与测距一致；导入方向正确；从地图、模型、导航到弹丸碰撞的坐标一致。

来源：[glTF 坐标标准](https://github.com/KhronosGroup/glTF/blob/main/specification/2.0/Specification.adoc#coordinate-system-and-units)、[Camera](https://threejs.org/docs/pages/Camera.html)、[交接地图说明](handoff/current/04_CAMPAIGN_AND_LEVELS.md)。

## 3 主循环与时间

API 事实：`Timer` 可在同一更新后返回一致的时间增量，并支持页面可见性处理；`AnimationMixer.update()` 的增量单位为秒。

工程建议：仿真以固定 60 Hz 为起点，渲染独立；设置单帧最大累计步数和暂停恢复策略，防止切回窗口后一次补算数秒。具体频率以弹丸、碰撞与目标硬件验证决定。

移动、射速、冷却、动画和音效调度读取明确的游戏时间。镜头后坐力与呼吸不累计写回角色物理坐标。输入意图、物理更新、任务事件与表现更新有固定顺序；不要让不同模块反复读取并推进不同的时钟。

验收：30／60／高刷新率下移动距离和射速一致；暂停不继续扣弹或推进任务；恢复不瞬移、不补发一串子弹。物理步内的弹丸扫掠仍需覆盖高速飞行，不能只依赖提高帧率。

来源：[Timer](https://threejs.org/docs/pages/Timer.html)、[AnimationMixer](https://threejs.org/docs/pages/AnimationMixer.html)。

## 4 输入、相机与移动

API 事实：`PointerLockControls` 提供锁鼠标、灵敏度、俯仰范围与锁定事件。它不自动提供完整人物物理、蹲伏、冲刺、ADS 或任务控制权。

项目要求：WASD、鼠标观察、右键 ADS、左键射击、R 换弹、空格跳跃、C 蹲姿、E 情境交互；映射可按目标设备调整。成人走／跑／蹲行从 2.1／6.3／1.35 m/s 开始。无体力条；运动与动作播放倍率分离。

工程要求：

- 用按键状态与一次性按下事件区分持续输入和单次动作。
- 失焦、暂停、死亡、控制权转移时清理旧按键和鼠标按钮；恢复锁定须经有效用户操作。
- 偏航、俯仰、相机晃动与身体朝向分别处理；俯仰限制防止翻转。
- ADS 明确视野、灵敏度和武器瞄具变换；冲刺退出 ADS，装填与切换状态不可互相抢占。
- 调试自由观察隔离游戏输入，返回原人物位置与朝向，不改变任务进度。

验收：大角度连续转向、贴边转向、跳跃＋装填、多键并按、ESC、Alt／Command-Tab、右键、重新进入窗口；均无粘键、跳视角和意外发射。

来源：[PointerLockControls](https://threejs.org/docs/pages/PointerLockControls.html)、[交接玩法规范](handoff/current/05_GAMEPLAY_AND_PRESENTATION.md)。

## 5 人物碰撞与导航

官方 `games_fps` 展示胶囊人物和 Octree 场景碰撞，可作为静态环境基础。它不是自动解决动态门、移动平台、复杂 NPC 导航或全部 FPS 行为的引擎。

工程建议：静态场景采用简化碰撞网格＋Capsule／Octree 路线先验证；动态门与可移动道具独立更新碰撞。需要更复杂动态交互时再比较专用物理方案，不在文档阶段同时引入多个物理引擎。

可见几何、碰撞几何、导航数据承担不同职责；保持空间与状态一致。蹲下改变胶囊时检查头顶空间，起身不能穿过低梁；接地、斜坡、台阶和落地分别测试。重力继承约 1.428 m/s²，牵引鞋的人员接地控制不改变弹丸或落物重力。

当前患者车采用完整床体长方盒、1.3米导航净空和同向车距；旁侧步道只给可步行者。普通角色之间仍不互相挤压，不能据此宣称完整拥挤模拟。

验收：墙角滑动、斜坡、门槛、蹲姿起身、跳跃撞顶、从掩体撤回、窄口会车、动态门切换、NPC 让路。高精美术的细碎三角面不直接决定全部寻路成本。

来源：[Octree](https://threejs.org/docs/pages/Octree.html)、[官方 FPS 示例](https://threejs.org/examples/games_fps.html)。

## 6 飞行弹丸与伤害

项目要求：弹丸有飞行时间，受当地重力和设定大气阻力影响。每发至少记录稳定 ID、发射者、武器、位置、速度、发射时间、寿命和已命中状态。初速、阻力参数和伤害由武器定型后校准。

每个物理步先推进弹丸，再对上一位置到下一位置的线段进行碰撞查询，取本步最近有效碰撞，避免穿过薄墙和重复伤害。移动目标的相对运动需通过固定步长、合适子步或相对扫掠验证，不能假定仅检测终点足够。

`Raycaster` 可以用于这个短线段，也可以用来从准星获取瞄准目标。它返回按距离排序的交点并支持图层过滤；使用它不意味着采用即时全射程 hitscan。

规则：

- 先统一准星选点、枪口位置与弹丸初始方向，再检查枪口到发射位置的遮挡；不从墙后开火。
- 墙体、敌方命中体、友方与装饰分别过滤；手臂、枪械和枪口效果不击中自己。
- 生命值与部位伤害由命中事件处理，视觉粒子不直接修改任务状态。
- 对友方给停火反馈；不新增平民随机死亡或玩家友伤分支。
- 发射率、弹匣、装填、切枪和动画由同一武器状态协调；同一事件只扣弹、加弹一次。
- 弹丸、弹孔、弹壳和短时特效分别设置生命周期与数量上限。

验收：远近目标到达时间不同；相同初速下下坠符合配置；薄墙不穿透；近墙无枪口穿墙伤害；暂停、死亡和重试清除旧弹丸；高低帧率射速一致。

来源：[Raycaster](https://threejs.org/docs/pages/Raycaster.html)、[交接弹丸要求](handoff/current/05_GAMEPLAY_AND_PRESENTATION.md)。

## 7 第一人称武器、角色与动画

第一人称 Viewmodel 与世界角色有不同的近距离要求。建议分开管理手臂／枪械显示与世界身体；是否使用独立渲染层或相机由穿模、视野和阴影验证决定。视觉处理不能绕过真实枪口遮挡。

工程要求：骨架、权重、动作片段和动画混合逐项验收。语义动作映射不绑定生成工具的随机 clip 名称；至少覆盖 idle、walk、run、crouch、aim、fire、reload、hit、death。命名为项目约定，不是 Three.js 强制命名。

根运动与代码位移必须明确所有权，不叠加两份位移。素材按原速起步，按角色步幅和步态匹配；不以统一快放追赶奔跑速度。换弹入出混合、手握武器、弹匣与枪机接触按事件时刻验证。

敌人死亡后停止感知、瞄准与伤害，完成倒地，再按可见性与预算回收。周延的医疗死亡是剧情人物状态，不使用普通敌人淡出规则。

验收：从正面、侧面、第一人称最近距离看手脚与道具接触；重复进入与中断动作不失步；死亡不直立、不继续开火；移动速度变更不机械带动全部动画倍速。

来源：[AnimationMixer](https://threejs.org/docs/pages/AnimationMixer.html)、[AnimationAction](https://threejs.org/docs/pages/AnimationAction.html)、[旧原型经验](handoff/current/09_PROTOTYPE_LESSONS.md)。

## 8 NPC、遭遇与任务事实

敌人需要可解释的感知、遮护、射界、装填、换位、寻找、受击和退出。丢失视线不能隔墙持续精确追踪。敌军入场要有道路和预告，玩家占据入口时延迟尚未进入的队伍。

遭遇状态与 NPC 行为分离。场景事实决定阶段，敌人数只控制压力；人员到达、设备就绪、阵位交接或路线关闭可结束战斗并停止增援。不用无敌末兵、隐藏残兵或等待秒数补时长。

北闸四阶段原型的 8＋12＋10＋14、7 名工人、同场上限 8 是旧版证据与起点。全片 256—348 是候选入场预算，不是当前实际人数或击杀配额。

验收：工人和队友真实移动到位；NPC 不堵住唯一退路；目标完成后增援停止、剩余远处敌人可以撤退；打空弹匣、漏听报点和走错掩体后仍有合理恢复空间。

参考：[DIVE 作者说明](https://discourse.threejs.org/t/game-ai-how-to-implement-a-basic-deathmatch-shooter/7609)、[战役与遭遇](handoff/current/04_CAMPAIGN_AND_LEVELS.md)。

## 9 控制权、知识状态与存档

四类控制权为作战、工作、协作和固定演出。每段声明允许的操作、进入条件、人物锚点、退出条件、跳过终态与检查点。协作动作先提示占用双手，在玩家确认后进入。

角色已知信息与玩家跨视点见闻分开记录。闻川不能因为玩家刚体验了周延的视点，就提前知道被隐瞒的消息。任务栏、终端、对白和无线电读取同一知识状态。

检查点恢复玩家、弹药、NPC、任务、波次、门、物件、信息和演出状态，重复恢复应得到同一结果。剧情固定重伤不通过扣空普通生命值伪装失败；跳过只跳已允许的演出，不替玩家完成未结束的战斗。

验收：S01／S02 视点切换与坍塌后状态一致；S08 无假追击目标；S09 接防确实完成；S10—S11 正常播放与跳过到达同一剧情终态。普通死亡和重试不会更改固定结局。

来源：[人物因果](handoff/current/03_CHARACTERS_AND_ARCS.md)、[玩法与演出](handoff/current/05_GAMEPLAY_AND_PRESENTATION.md)。

## 10 世界表现、HUD 与声音

天空与地图共享世界方向；木星不跟随相机视角旋转。地球化、空气、温度和工作点按创作设定处理，不写成本次真实气候或星历模拟结果。

HUD 保留准星、弹药、可读任务、交互、必要受击方向和离屏目标。中文底部字幕显示说话者；支持字号调整和关键提示回看。长争执、取舍与医疗对白安排在安全段，战斗中使用短报点。

声音区分世界空间声与非空间 UI／无线电，控制同时播放数量和优先级；枪声、危险方向和任务报点不被背景音乐压住。演出音频随暂停、跳过和重试正确结束。

验收：第一人称和自由观察均无浮空／穿模；角色站偏、看向旁边仍能获得关键事实；目标在背后可定位；字幕与交互提示不重叠。

## 11 性能、加载与资源回收

以目标机实测确定预算，记录分辨率、设备像素比、画质档、浏览器／Electron 版本、场景状态、CPU／GPU 时间和可用渲染统计。1080p／60fps 是目标，单帧预算约 16.7ms，不是所有 Mac 或 Windows 机器的性能承诺。

资产按首段需要加载，后续区域按关卡规划加载；进度和错误可见。复用几何／材质、限制阴影灯与透明叠加、特效对象池、合适 LOD 和纹理压缩均按测量采用，不为所有模型套相同面数。

切场景和重试时释放不再使用的几何、材质、纹理、动画、监听与音频；共享资源采用所有权或引用计数，不能被一个实例提前销毁。截图不能证明帧时间或长期内存稳定。

验收：多次死亡重试与切场景后资源数量无持续增长；最大战斗压力、近景角色和救援演出都测量；首次加载和离线重新启动通过。

来源：[WebGLRenderer](https://threejs.org/docs/pages/WebGLRenderer.html)、[LoadingManager](https://threejs.org/docs/pages/LoadingManager.html)、[GLTFLoader](https://threejs.org/docs/pages/GLTFLoader.html)。

## 12 Windows EXE 与验收证据

Electron 可将 Web 技术封装为 Windows 桌面应用，但浏览器可玩不等于 Windows 交付通过。具体选择便携目录、安装包还是其他分发形式，在打包验证时明确。

候选实现将渲染进程与平台适配分开，游戏资源及解码器随包，存档使用明确可写位置；不依赖 CDN、当前工作目录或 Mac 绝对路径。窗口切换、全屏、分辨率、鼠标锁定、音频设备和退出保存需在目标 Windows 验证。

Electron Forge 的 Squirrel.Windows 产物是安装器 `Setup.exe`；官方对其构建主机有限制，不能把 Mac 开发服务运行通过当作已产出 Windows 包。后续按所选打包方案安排 Windows 构建机或适用 CI。

完成证据至少包括：版本提交、机器与分辨率、真实输入、任务推进、死亡／重试、演出跳过、资源加载、正常速度录像、性能记录和未测项。自动化与真人观察分别记录。

来源：[Electron](https://www.electronjs.org/docs/latest/)、[Squirrel.Windows 构建要求](https://www.electronforge.io/config/makers/squirrel.windows)。
