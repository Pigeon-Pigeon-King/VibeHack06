# FPS 基础选型与当前版本诊断

核对日期：2026-10-30。项目：重返木卫三；历史目录沿用“重返木卫六”。

本轮完成了当前代码核对、GitHub 源码阅读、两个候选在线演示的操作检查，以及 Hyper3D 文档核对。当前游戏没有换引擎、改参数或替换资产。sources/ 保存 28 份关键源码、说明和许可证，供后续改造查阅；这里不是可以直接启动的完整仓库，也没有下载这些仓库的完整模型包。

## 当前版本为什么仍像原型

北闸试玩版的 controls.js、game.js、world.js、actor-motion.js、weapon-rig.js 和 projectiles.js 是围绕项目逐项编写的实现。它使用 Three.js，但没有直接采用一套完整的 FPS 模板，也没有接入 Rapier、Ammo 或 Yuka 的成套控制与行为系统。

上轮修复了具体错误：移动速度回到步行 2.1、跑步 6.3、蹲行 1.35 m/s；人物动作恢复素材原始节奏，倒地动作不再刻意拉长。修复这些错误能改善操作，却不能独自形成成熟射击游戏的整体体验。

当前需要连贯处理的内容是：

- 角色移动、贴墙、台阶、跳跃、蹲起和视线高度，应共用清晰的空间尺度与碰撞规则。
- 腰射、开镜、奔跑、开火、换弹、受击必须有一致的动作切换与中断规则。子弹、声音、枪口火焰、弹壳、后坐力和 HUD 应跟随同一次动作事件。
- 第一人称手臂和枪械需要一起制作并校准动画。只移动一个持枪模型，无法替代握持、拉栓、卸弹匣和复位等动作。
- 敌人需要有持续的感知、寻路、寻找射界、利用掩体、受击和死亡过程；增加总敌人数无法替代这些行为。
- 建筑结构、物件尺度、材质、照明和掩体的环境理由需要统一。程序通过通关检查，不代表画面和手感已经完成。

这些是结合源码与用户试玩反馈得到的工程判断；本轮没有重新给北闸做整关通关测试。

## 本轮实际演示检查

使用项目已有测试浏览器，另开隔离上下文运行原站，没有操作用户的试玩页面。

1. [Enari 在线演示](https://enari-engine.vercel.app/)：泳池地图加载成功。进入 Pointer Lock，输入前移、开火和换弹；观察到枪械及手臂的换弹姿态，前移后场景位置变化。
2. [FPP/TPP Starter 在线演示](https://fpp-tpp-shooter-starter.vercel.app/)：首次页面导航超过 20 秒，随后加载完成；选择 Y Bot 和 Industrial Yard，进入 Pointer Lock，前移、开火、换弹。弹量由 30 降至 27，出现 reloading 状态及换弹姿态。

两者实际画面均未达到本项目想要的现代战役完成度。以上为短时操作与画面检查，没有完成敌人战斗、音频评价、全动作遍历或性能基准。在线部署版本未核对到源码提交；保存的源码版本见 sources.json。

## 后续改造的具体方向

先在北闸制作一段能反复玩的短交战作为对照，再迁移到其余章节。这段需要一把制作完整的枪、一套匹配的第一人称手臂动画、两类敌人和一处完整场景。已有剧情、地图和资产继续使用。

建议选一套 Three.js + Rapier 控制基础，统一替换当前玩家碰撞与移动实现；同时用 Enari 和 Starter 的状态/显示分离方式改造武器系统。Ammo 示例的行为设计可以参考，实际运行时不叠加两套物理引擎。最终采用哪个控制实现，以载入北闸资产后的操作结果决定。

制作顺序：

1. 控制：先验证移动、连续转向、贴墙、跳跃、蹲起、坡面与台阶，保持当前用户要求的移动速度。世界单位继续采用米，重力为木卫三设定的 1.428 m/s²。
2. 枪械：统一开镜、开火、换弹和奔跑切换；匹配原始动作时长、声音和弹匣变化。移动速度与动画播放倍率分别管理，不能用全局 timeScale 改走路或死亡节奏。
3. 弹道与反馈：保留有限速度弹丸、逐帧扫掠碰撞和木卫三重力；从模板迁移时，不把瞬时 raycast 伤害判定带回来。射线仍可用于可见性、瞄点和弹丸一帧行程的碰撞检测。
4. 敌人：验证从警戒、接敌、移动到掩体、探身开火、受击、倒地到尸体淡出的连续过程，保持死亡动作素材的正常速度。
5. 场景：对一处建筑内外、车辆或货物形成的掩体、入口视线和灯光做完整处理；同一段连续录制自由移动、射击和敌人反应，直接看是否仍有漂移、跳帧、穿模和悬浮。

评价应包括连续移动时的手感、枪械动作衔接、命中反馈和敌人应对。自动通关、击杀数和没有报错仍可检查功能，但不能代替这些评价。
